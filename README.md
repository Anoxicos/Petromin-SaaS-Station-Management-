# Station Platform

Working prototype of a multi-client station operations platform. The staff app currently covers daily operations, credit/invoices, stock, reports, staged imports, and an M8 provider administration workspace. Database and Docker checks cover the buildable scope; authenticated client acceptance, production operating targets, legal configuration, and support terms remain outstanding.

## Current foundation

- PostgreSQL schema for clients, users, client/station memberships, stations, and append-only audit events.
- Row-level security policies for client-scoped tables.
- Per-station meter mode, closing cut-off, and IANA time zone.
- OIDC JWT verification through configurable issuer, audience, and JWKS URL.
- Verified subjects resolved to provisioned users and client memberships.
- Auth0 Authorization Code sign-in at `/login`, with state/nonce checks, PKCE S256, verified ID token, an HTTP-only access-token cookie, and local logout at `/logout`.
- Production image (`Dockerfile.production`) compiles TypeScript to JavaScript and runs with production-only dependencies as a non-root user. `compose.production.yaml` provides a private PostgreSQL service, ordered migrations, local snapshot service, and Caddy TLS reverse proxy for a generic Linux cloud VM; provider selection and production acceptance remain open.
- `npm run test:auth` runs an isolated local mock OIDC flow covering state/nonce/JWT rejection, PKCE challenge/verifier matching, callback token exchange, allowlisted return paths, cookie flags/clearing, external redirect rejection, HTML escaping, and failure responses. This verifies implementation behavior; it does not replace a real Auth0 account walkthrough.
- `npm run test:load` runs the read-only pilot benchmark against a local synthetic report endpoint and checks warm-up, request/concurrency counts, report schema checks, summary metrics, remote-target opt-in, and configuration limits. It validates the harness only; pilot load evidence still requires an authenticated pilot account and client-approved volume targets.
- CI runs `scripts/metrics-endpoint-test.mjs` inside the app container to verify the private metrics listener, bounded labels, request latency/counters, process/database gauges, and unsupported-path rejection.
- CI validates Prometheus scrape and alert-rule files and confirms the collector records the running app target.
- Client/station setup endpoints with server-side role checks and audit records.
- Transaction-local tenant context for PostgreSQL row-level security.
- Database-aware health endpoint.
- Tenant-scoped membership listing and audited updates, with owner-role protections.

## M2 data model in progress

- Client-owned product catalog and per-station product assignments.
- In `/app`, owners and managers can create client products and assign them to a station; add effective-dated fuel tariffs; add pumps, meters, nozzles, and tanks; record nozzle-to-tank assignment history; draft/activate tank calibration charts from supplied points; and record/view meter reset history. Setup writes use the existing audited APIs and role checks.
- Effective-dated station fuel tariffs with database-enforced non-overlapping periods.
- Station equipment identities and historical nozzle-to-tank assignments, constrained to compatible fuel products.
- Row-level security on all new catalog and station tables. `db/tests/m2_catalog_security.sql` runs rollback-only checks for tenant/station visibility and tariff/equipment constraints.
- Audited APIs for client products, station assignments, effective-dated tariffs, equipment, and nozzle-to-tank assignment history. Managers/owners can write; station access and tenant isolation are enforced server-side and in PostgreSQL.
- Station-day meter-reading batches for both nozzle and pump/totalizer station modes. Operators can replace draft batches, validation calculates volume and locks the batch, and authorized managers can correct the latest validated reading with a reason and append-only correction history.

### Meter-reading API

- `POST /stations/{stationId}/readings` creates or replaces the draft batch for one business date. Nozzle-mode entries reference a nozzle; product is determined from its station setup. Pump-totalizer entries reference a pump or meter and require `productAllocations`, for example `[{ "productId": "fuel-uuid", "volume": "3.250" }]`; allocation volumes must add up exactly to the final index less the initial index. This preserves a product-level fuel volume when one totalizer covers multiple fuels. Resubmitting a date replaces only a still-draft batch.
- `GET /stations/{stationId}/readings?date=YYYY-MM-DD` lists batches and readings, including correction history. Use `before=YYYY-MM-DD` to get only the latest validated prior reading for each active meter, plus that date's authorized reset starting index, for efficient daily entry prefill; `date` and `before` cannot be combined. Omit both to list full station history.
- `POST /stations/{stationId}/readings/{batchId}/validate` validates the draft, rejects lower or duplicate readings, computes each volume as final minus initial, records the validator, and locks the batch.
- `PATCH /stations/{stationId}/readings/{readingId}` corrects the latest validated reading. The JSON body requires `initialIndex`, `finalIndex`, and a non-empty `reason`; only an owner, manager, or super-admin may do this. The before/after values and approving actor are retained in an append-only correction record and audit event. If that station day is already closed, the same transaction also appends a numbered immutable closing adjustment with before/after meter values; the original close snapshot remains unchanged.
- `POST /stations/{stationId}/equipment/{equipmentId}/meter-resets` records an authorized meter replacement/reset with `{ "businessDate": "YYYY-MM-DD", "previousIndex": "510.000", "newInitialIndex": "5.000", "newSerialNumber": "optional", "reason": "Meter replaced" }`. `previousIndex` must match the latest validated reading. A lower index is accepted only for that meter and date when the new reading starts exactly at the recorded new index. `GET` on the same route lists the immutable reset history.
- `GET /stations/{stationId}/day-inputs?date=YYYY-MM-DD` retrieves a station day's cash/card totals, their currency, and tank dips. `PUT` on the same route saves or updates draft inputs with `{ "cashTotal": "1200.00", "cardTotal": "350.00", "currencyCode": "MAD", "dips": [{ "tankId": "<tank-uuid>", "productDepthMm": "1250.000", "waterDepthMm": "12.000" }] }`. The three-letter currency is explicit per station-day; no currency is assumed. Cash and card are collection totals, separate from meter-derived sales; dips store measured depth in millimetres and convert to volume only when an active dated tank calibration chart covers the measurement. `POST /stations/{stationId}/day-inputs/{YYYY-MM-DD}/validate` requires a currency and one dip for each active station tank, records the validator, and locks the inputs. Reconciliation must use that same currency. All changes are audited and tenant-scoped.
- `GET /stations/{stationId}/financial-variance-thresholds` reads optional cash/card tolerances. Owner/manager `PATCH` sets `{ "currencyCode": "MAD", "maxAbsCashVariance": "10.00", "maxAbsCardVariance": "2.50", "reason": "Approved operations policy" }`; either tolerance can be left null, and leaving both null clears the policy. There is no default amount. `GET /stations/{stationId}/day-inputs/{YYYY-MM-DD}/reconciliations` returns immutable revisions; `POST` records counted cash, card settlement, optional settlement reference, note, and the currency code used for those amounts. The API snapshots the current policy and classifies each variance against it. A later recount is a new revision; records cannot be edited. Reconciliation is informational and never blocks closing.
- `GET /stations/{stationId}/daily-state?date=YYYY-MM-DD` gives an access-controlled, read-only daily overview: validated fuel volumes by product, cash/card collection totals, the latest manual cash/card comparison, tank dips, and whether readings and day inputs are validated. `closingWindow` reports the configured local start/end instants and whether the station cut-off has passed. `readyToClose` remains false until both daily inputs are validated, the cut-off is reached, and a closing-day rule is configured.
- Daily state also reports an estimated fuel sales value when the station has a `closingDayRule` and one effective tariff covers the whole business-day interval for every metered fuel. Station settings accept `closingDayRule: "CUTOFF_STARTS_DAY"` or `"CUTOFF_ENDS_DAY"`; omit it to leave unset, or send `null` to clear it. Until chosen, or when a product has a tariff gap or intraday tariff change, the relevant value remains unpriced and the API reports why. This estimate values meter volumes only; it does not allocate cash/card/credit tender or represent an issued sale/invoice.
- `POST /stations/{stationId}/daily-closing?date=YYYY-MM-DD` records an immutable operational close once meter readings and cash/card plus all active tank dips are validated and the configured station business-day window has ended. The station must have a `closingDayRule`; the endpoint rejects a close before that time-zone-aware cut-off. It saves the exact window and a snapshot/audit event, including the latest manual cash/card reconciliation when present. Cash/card and fuel-stock variance policies provide review flags only; no variance threshold blocks close.
- `GET /stations/{stationId}/daily-closing?date=YYYY-MM-DD` retrieves the original snapshot, latest adjusted snapshot if present, closing metadata, and the full adjustment history.
- `POST /stations/{stationId}/daily-closing/{closingId}/adjustments` lets an owner, manager, or super-admin correct cash/card totals and/or the full set of active-tank dips after closing. A reason is required; the API saves immutable before/after snapshots and an audit event without changing the original close. `GET` on the same route returns the adjustment history. Meter corrections continue through the separate audited meter-reading correction workflow.
- `GET /stations/{stationId}/tanks/{tankId}/calibrations` lists the tank's calibration history. `POST` on that route creates a draft using `{ "effectiveFrom": "YYYY-MM-DD", "points": [{ "depthMm": "0", "volumeLiters": "0" }, { "depthMm": "1000", "volumeLiters": "5000" }] }`; managers, owners, or super-admins activate it at `/stations/{stationId}/tanks/{tankId}/calibrations/{calibrationId}/activate`. Points must increase in both dimensions; active curves are immutable and later curves take effect on a later date. Dips convert by linear interpolation between supplied points; values outside the curve's range remain unconverted. Provide the actual tank calibration chart before activation.
- All endpoints require a verified OIDC bearer token and `X-Client-Id`. Station access and tenant isolation are checked in the API and PostgreSQL row-level security.

## Provisional technical choices

PostgreSQL 16+ and Docker Desktop are confirmed. TypeScript remains the working language choice. The application and database both enforce tenant boundaries.

## Local setup

1. Install Docker Desktop and start its Linux container engine.
2. Copy `.env.example` to `.env`; set `POSTGRES_PASSWORD` to a strong local-only value. Compose applies it to both local database roles.
3. Set `AUTH_ISSUER`, `AUTH_AUDIENCE`, and `AUTH_JWKS_URL` for the OIDC provider. For Auth0 browser sign-in, also set `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`, and `AUTH0_CALLBACK_URL`.
4. Run `docker compose up --build`.
5. Open `http://localhost:3000/health` to see the service health response.

Compose runs PostgreSQL 16, creates a non-login schema owner and a separate `NOBYPASSRLS` application role, applies tracked SQL migrations before the app starts, and writes an atomic rolling database snapshot to a separate Docker volume. The default backup interval is 24 hours and can be changed with `BACKUP_INTERVAL_SECONDS`. Set `OFFSITE_RESTIC_REPOSITORY` and a strong, unique `RESTIC_PASSWORD` to also write encrypted snapshots to a Restic repository, including S3-compatible object storage; provide the compatible access key, secret, session token, and region as required by the selected endpoint. Off-site recovery remains disabled until configured. Optional rolling retention flags are unset by default, so old remote snapshots are not deleted automatically; obtain a retention policy before enabling pruning. After adding a migration, run `docker compose run --rm migrate` before deploying the updated app. Each migration runs in a database transaction and is recorded only after success. The runner recognizes and records the previously initialized schema after checking required tables, columns, and grants; it stops rather than guessing if that schema is incomplete.

Docker health checks monitor PostgreSQL connectivity, the app `/health` route, and backup freshness against twice the configured interval. When an off-site repository is configured, backup health also depends on a recent successful remote upload. App requests emit structured JSON logs with a response request ID and route category; response bodies, paths, query strings, identifiers, and headers are excluded. Local snapshots alone do not provide off-site protection, and a configured remote repository does not establish a contractual RPO/RTO or production recovery readiness. Follow [the operations runbook](docs/operations-runbook.md) for backup and restore procedures.

The app exposes Prometheus text metrics at `http://app:9464/metrics` on the private Docker network. A Prometheus service scrapes the app and itself; its development console is available at `http://localhost:9090`, while production publishes no console port. Metrics include only bounded route/method/status classes, request latency, process usage, and database pool counts; they exclude tenant, user, path, and business transaction labels. A one-minute target-unavailable rule is loaded, but notification routing and SLO thresholds remain unset. The sample config keeps aggregate metrics for 15 days; change that separately from client-record retention.

The initial migration creates tables and RLS policies. Do not expose the service to client traffic until production secrets, callback/logout origins, and data-protection terms are set. Locally, open `http://localhost:3000/login` to sign in through Auth0; the callback shows the authenticated account's exact `sub`, email, and name. From `/app`, the Sign in link returns to station operations after authentication; a direct `/login` continues to show the verified identity for initial administrator setup. If the access token expires, the app clears the selected client and station and hides operational data until sign-in completes. The client and station picker only lists workspaces and stations permitted for the signed-in user; tenant API requests continue to require and verify the selected `X-Client-Id`. Use the one-time SQL bootstrap only for the intended administrator: `docker compose exec -it db psql -U station_admin -d station_platform -f /scripts/bootstrap_super_admin.sql`. It prompts for those three values and refuses to proceed if a super-admin already exists. Thereafter authenticated super-admins can provision users at `POST /admin/users`. Tenant owners/managers can list memberships at `GET /clients/{clientId}/memberships`, add one at `POST /clients/{clientId}/memberships`, and change its role or station assignments at `PATCH /clients/{clientId}/memberships/{userId}`. Managers cannot grant the owner role, and the last client owner cannot be demoted. Owners/managers can create stations at `POST /clients/{clientId}/stations`; owners/managers and super-admins can update station meter mode, closing cut-off, and time zone at `PATCH /stations/{stationId}/settings`. Membership and station-setting changes are recorded in the append-only audit log.

To restore a snapshot without overwriting the active database, run `docker compose exec backup sh /scripts/restore-latest.sh station_platform_restore`. The target database name must be new. The restore script restores under the schema-owner role, verifies that migration history matches the active source, checks row-level security and app-role privileges, and reports observed snapshot age and restore time. These local measurements are not production RPO/RTO guarantees.

When off-site Restic is configured, restore into a different new database with `docker compose exec backup sh /scripts/restore-offsite.sh station_platform_offsite_restore`. This fetches the latest encrypted repository snapshot into temporary storage, verifies the snapshot's completion marker, then runs the same schema and tenant-security checks. It never replaces the local snapshot or active database. Run this against the actual approved object-storage endpoint before onboarding client data; CI's local filesystem repository check only verifies encryption and restore flow.

## M3 credit and invoice foundation

- `/app` now provides customer/credit setup, multi-line station sales and tenders, voucher issuance/status/redemption, payment recording and credit-sale allocations, accountant-gated invoice-profile editing/approval, invoice issue/print, and credit-note issue/history. Prices, currencies, tax rules, number prefixes, and credit-note receivable adjustments require explicit supplied values.
- `GET/POST /customers` lists or creates tenant customers. `GET/PUT /customers/{customerId}/credit-account` reads or sets a manager-controlled credit limit, terms-days field, and account status.
- `POST /stations/{stationId}/sales` posts an immutable sale with line snapshots and tenders. Each line supplies `description`, `unitCode`, `quantity`, `unitPrice`, `taxCode` (optional), and `taxRatePercent`; fuel prices must match the dated station tariff effective when the sale is created. The tax rate is preserved as entered and is not a legal assertion until the client accountant approves a profile. Tenders use `CASH`, `CARD`, `CREDIT`, or `VOUCHER`. Credit-limit overrides require owner/manager authorization, a reason, and an audit record. `GET /stations/{stationId}/sales/{saleId}` returns the immutable sale details.
- `GET /stations/{stationId}/sales` lists recent accessible station sales with current outstanding credit, any issued invoice reference, and recorded installment payments. Later customer payments can be allocated to the sale or to a selected remaining installment. The database enforces installment caps; after a credit note adjusts the receivable, allocation stays at sale level until the client defines how credits map to installments.
- Credit sales snapshot the account's configured payment terms or a transaction-specific installment schedule. If no terms are configured, the sale has no due date unless a schedule is entered. Later account-term changes do not rewrite old sales. Installments must total the credit tender; no interest, late fee, or legal delinquency policy is assumed. Payments still allocate against a sale's outstanding balance rather than a specific installment.
- `POST /customer-payments` records a customer payment and can allocate parts of it to earlier credit sales using `allocations: [{"saleId":"…","amount":"…","installmentNumber":1}]`. `installmentNumber` is optional for sale-level allocation; when supplied it must identify a saved schedule installment and cannot exceed its remaining scheduled amount. For a scheduled sale, sale-level and installment-specific allocations cannot be mixed. After a credit-note receivable adjustment, allocate at sale level until the client defines how that adjustment maps to installments; a receivable-adjusting credit note is blocked after installment-specific payments. Allocations reduce receivables and never create sales.
- `GET/POST /vouchers` lists balances or issues a tenant voucher. `PATCH /vouchers/{voucherId}/status` activates, suspends, or expires it. Sale redemption is recorded through a `VOUCHER` tender and updates the locked voucher balance when the sale posts. `POST /vouchers/{voucherId}/cancel` lets an owner or manager cancel an active/suspended voucher with a reason; it appends a cancellation movement for the remaining balance while preserving redemption movements.
- `GET/PUT /client/invoice-profile` reads or drafts a tenant invoice configuration, including `issuerName`, `legalMentions`, `taxRules`, and the invoice/credit-note prefixes. A user with the client `ACCOUNTANT` role must explicitly approve it at `POST /client/invoice-profile/approve` with an approval statement and optional reference. Every line's tax code and rate must match an approved tax rule before an invoice can be issued.
- `POST /stations/{stationId}/sales/{saleId}/invoice` issues an immutable, numbered invoice snapshot from a posted sale. `GET` on that route returns it. `GET /invoices/{invoiceId}/print` serves a print-ready view; `/app` has an invoice-ID print control that keeps the selected client context. `GET/POST /invoices/{invoiceId}/credit-notes` lists or issues immutable credit notes; `receivableAdjustment` states how much of the note reduces that sale's customer receivable. `GET /credit-notes/{creditNoteId}/print` serves a tenant-scoped print/save-as-PDF view based on the immutable credit note and linked invoice snapshots.
- Issued invoices freeze the customer's name, code, email, and phone as displayed at issue time; invoice and credit-note print views use that snapshot even if the customer record later changes. A migration of older invoices seeds the snapshot from the customer details currently displayed at cutover, since the earlier version did not retain buyer details separately.
- Invoice issuance is blocked until client-approved legal configuration exists. The profile stores flexible supplied rules and an accountant attestation; it does not determine whether those rules satisfy local law. Invoices can be printed or saved as PDF through the browser; direct PDF file generation, client-provided VAT/legal rules, interest/delinquency policy, and authenticated acceptance are still outstanding.

## M4 stock, purchases, and services

- `/app` provides owner/manager workflows for client suppliers, multi-line supplier receipts, reasoned stock adjustments/opening balances, recipe configuration for service component articles, and read-only stock movement/receipt history. It refreshes inventory after each posted movement. Currency, dates, unit costs, quantities, and adjustment reasons must be entered from the client's records; no variance threshold is assumed.

- `GET/POST /suppliers` lists or creates tenant suppliers.
- `POST /stations/{stationId}/purchase-receipts` records and posts a supplier receipt with `{ "supplierId":"…", "businessDate":"YYYY-MM-DD", "currencyCode":"MAD", "lines":[{"productId":"…","tankId":"…","quantity":"1000.000","unitCost":"10.0000"}] }`. Fuel receipts require an active matching tank. Posting creates immutable stock movements.
- `GET /stations/{stationId}/purchase-receipts` lists posted receipts and their line details.
- `POST /stations/{stationId}/stock-adjustments` records an owner/manager adjustment or opening balance with a non-zero quantity delta and reason. `GET /stations/{stationId}/stock-movements` returns the immutable movement history, optionally filtered by `productId`.
- `GET /stations/{stationId}/inventory?date=YYYY-MM-DD` reports article stock from receipts, sales, service consumption, and adjustments. For fuel it adds receipts/opening movements and subtracts current validated meter volumes; when every active tank has a validated dip and a supplied calibration curve covering both product and water depths, it includes net dipped volume and the raw variance. No tolerance is inferred or used as a close blocker.
- Fuel variance review tolerances are optional, station- and fuel-product-specific settings: `GET /stations/{stationId}/variance-thresholds` lists them and owner/manager `PATCH` accepts `{ "productId": "…", "maxAbsVariance": "25.000", "reason": "Client-approved reference" }`; use `maxAbsVariance: null` to clear one. Values use that fuel product's configured unit, require an approval note/reference, and are audited. Inventory labels variances outside a configured absolute tolerance for review only. No tolerance is prefilled and no threshold blocks closing. Cash/card tolerances remain unconfigured while their unit/currency and escalation policy are undecided.
- `GET/PUT /stations/{stationId}/services/{serviceProductId}/components` reads or configures an audited service recipe. Posting a service sale consumes component articles through separate movements; it does not create article sales. Article sale lines consume their own stock when posted.

## M5 reporting and exports

- `GET /reports/daily-state?date=YYYY-MM-DD` consolidates accessible station status, product volumes, posted app-sale totals and credit sales by currency, cash/card inputs, dip readiness, and close status for the selected client. Posted sales are gross transaction totals; credit notes remain separate records in the accounting export. Each currency row also shows the current open balance of posted credit sales through the selected business date; later payments and credit notes affect that balance. Cash/card inputs remain separate from posted app sales, and imported opening balances without station-linked sales are not attributed to a station. `GET /reports/daily-state.xlsx?date=YYYY-MM-DD` downloads a native workbook with separate station and sales-by-currency sheets; the `.csv` endpoint remains available. `GET /reports/daily-state/print?date=YYYY-MM-DD` serves the print/save-as-PDF view; `/app` provides workbook and print actions.
- `GET /reports/accounting-export.xlsx?from=YYYY-MM-DD&to=YYYY-MM-DD` downloads a native workbook with separate sales, invoices, credit notes, customer payments, and purchase lines. Payment allocation details include the selected installment when supplied. The `.csv` endpoint remains available.
- `GET /reports/accounting-export.csv?from=YYYY-MM-DD&to=YYYY-MM-DD` downloads un-invoiced posted sales, issued invoices, credit notes, customer payments, and purchase receipt lines as distinct record types. Invoice-linked sales are represented by the invoice row, and customer payments stay separate from revenue.
- The accounting CSV is a neutral operational export. A target accounting format, account-code mapping, purchase VAT treatment, and connector behavior still need client-specific definition; no double-entry journal or tax mapping is guessed.
- CSV text cells beginning with spreadsheet formula markers are prefixed as text; ordinary signed numeric values remain numeric-compatible.

## M6 staged data imports

- `/app` accepts CSV and native `.xlsx` workbooks for general historical records, station opening stock, and opening customer receivables. It reads the first worksheet of an `.xlsx`; the downloadable header-only CSV template can be opened and saved as `.xlsx` in Excel. CSV quoting is validated; malformed quoted fields are rejected before staging. Product and customer codes are resolved within the selected tenant; station stock imports require a station and an active station-product assignment, and receivables require an active customer credit account.
- `POST /import-jobs` stages 1–5,000 rows (up to 5 MB of request data). `GET /import-jobs` lists recent jobs; `GET /import-jobs/{jobId}` returns their preview. `POST /import-jobs/{jobId}/validate` validates and freezes normalized rows. `POST /import-jobs/{jobId}/commit` appends the complete valid batch; a job with any invalid row cannot be committed. A corrected file is staged as a new job.
- Historical rows are an immutable archive and do not fabricate sales, invoices, tax treatment, or payments. Opening stock and receivables create reasoned ledger entries; receivables preserve the effective business date and source import row. Every stage, validation, and commit is audited and tenant-scoped. The 5,000-row job ceiling is a technical batch size, not a business history cap.
- `GET /import-history` browses committed archive rows with optional `from`, `to`, `stationId`, and exact `recordType` filters; it returns 100 rows per page by default, accepts `limit` up to 500, and provides an opaque `cursor` for older rows. `GET /import-history.csv` exports the filtered page with spreadsheet-formula protection. Only owners, managers, accountants, and super-admins can use the archive browser/export; station filters are checked against the selected client and user's station access.
- History date range, record quality, paper digitization responsibility, reconciliation evidence, and retention period still require client/provider decisions. These are not guessed by the import flow.

## M8 platform administration

- `/admin/platform` is a super-admin workspace for tenant overview, repeatable onboarding, plans, subscriptions, and monthly statement review. `POST /admin/platform/onboard` provisions a client, links an already provisioned owner by email, and creates 1–50 stations with explicit per-station meter/cutoff/time-zone settings in one transaction. The UI does not prefill those operating settings or the day-boundary convention. It does not create or guess an Auth0 subject; the owner must authenticate once before onboarding.
- `GET/POST /admin/platform/plans` manages flexible plan metadata. `POST /admin/platform/plans/{planId}/rates` adds an immutable effective-dated monthly base fee and per-station fee with an explicit currency. Zero rates are accepted only as explicit configured values; no default price or currency is applied.
- `GET/POST /admin/platform/clients/{clientId}/subscription` creates or views a pending subscription and requires an explicit billing day and IANA time zone. `PATCH /admin/platform/subscriptions/{subscriptionId}` changes status; activation requires a real contract reference. Plans and rates can be edited without choosing a tax rule or legal invoice wording.
- New clients receive a standard ten-item onboarding checklist for user access, station-day rules, products/prices, equipment/calibration, finance approval, stock rules, history reconciliation, privacy/retention, support/training, and pilot acceptance. `GET /clients/{clientId}/onboarding` shows it in `/app`; the assigned client role can close a task only with a completion note. Provider tasks are closed by the super-admin. Super-admins can waive a task with a recorded reason. Checklist readiness is not automatic pilot acceptance; signed client evidence is still required.
- `POST /admin/platform/clients/{clientId}/billing-statements` snapshots an active signed subscription's full calendar-month rate and station count into a draft pre-tax statement. The provider can review or void drafts; `GET /client/billing-statements` lets a client owner/accountant inspect their statements. These are internal statements only: no legal invoice, tax amount, payment collection, or external charge is created. Those steps remain dependent on contract, tax, invoice, and payment-term decisions.
- `GET /admin/platform/overview` is a support-oriented status view of client/station/user counts and subscription state; the onboarding panel provides checklist status/evidence notes and `GET /admin/platform/clients/{clientId}/audit-events` shows recent tenant audit events. Client owners/managers/accountants can view their own events at `GET /clients/{clientId}/audit-events`. These views do not expose station sales or operational records. Support channels and response targets remain to be agreed for M9.

## M9 support workflow

- Client members can create and view their tenant's support requests in `/app` using `POST/GET /client/support-requests`; they can read the conversation at `GET /client/support-requests/{id}/messages` and add a client-visible reply with `POST` to that route.
- Super-admins can inspect the provider queue at `/admin/platform`, open a request with `GET /admin/platform/support-requests/{id}`, transition its status with `PATCH`, and add a client-visible reply or provider-only note with `POST /admin/platform/support-requests/{id}/messages`. The assignment dropdown contains configured provider super-admin accounts; assignment can be cleared and the database rejects assignment to a client account. Status and assignment changes are recorded in the conversation and request-opening is audited. Database rules require messages to match the authenticated actor and prevent clients from forging status events or provider-only notes.
- The queue enforces allowed status transitions and requires a resolution note before resolution. Provider-only messages are not visible to the client. The UI warns users not to include credentials or payment-card data. No support channel, availability promise, or response target is implied; those terms remain to be agreed.
