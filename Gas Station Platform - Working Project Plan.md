**Working draft v1.92 — 15 October 2026**
Based on the supplied project brief and project skill. This is a living planning document; decisions marked **Provisional** are working assumptions and can be edited. Effort is sized S / M / L / XL because no start date or deadline has been set.

| Topic | Current position |

## 6. Checklist by module

### M01 — Multisite administration and users
- [x] Client (tenant) entity and tenant isolation; workspace discovery and database RLS are covered by rollback-only tests.
- [x] Station sheet with client-unique code (RG-001).
- [x] Per-station meter mode, closing cut-off, time zone, and cutoff convention; owner/manager setup is available in `/app`.
- [x] Users, roles, and permissions per client and station.
- [x] Super-admin role across clients.
- [x] Auth0 authorization-code callback validates state, PKCE S256, ID-token signature/issuer/audience/nonce, safe return route, and protected/cleared cookies; mock-provider regression runs in CI. Real-provider sign-in remains a pilot acceptance step.
- [x] Server-side authorization on operational API data (RG-002, RG-022); authenticated HTTP walkthrough is still needed before pilot.

### M02 — Products and tariffs
- [x] Product catalogue for fuels and other products; client product creation and station assignment are available in `/app`.
- [x] Tariff table with effective date/time and history; manager setup and overlapping-period rejection are covered.
- [x] Transaction price frozen at sale (RG-007); M3 sale lines retain the unit price and the database checks it against the effective station tariff.
- [x] Intraday price-change exception is explicit: a business day with multiple tariff periods is reported as unpriced rather than guessed (RG-008).

### M03 — Pumps, meters, nozzles, and tanks
- [x] Equipment has unique identity and assignment history (RG-003); owners/managers can create pumps, meters, nozzles, and tanks in `/app`.
- [x] Tank-to-nozzle assignment fixed at setup; versioned changes are audited and can be recorded in `/app`.
- [x] Authorized, reasoned meter replacement/reset record; `/app` exposes the audited form and history, and a lower index is accepted only on the recorded business date and exact new initial index (RG-004).

### M04 — Manual index readings
- [x] Nozzle-level or pump/totalizer entry according to station setting. Pump/totalizer mode requires product-volume allocations that sum exactly to the validated meter volume; nozzle mode derives product from equipment setup.
- [x] Volume uses final validated index less initial validated index (RG-004).
- [x] Daily entry prefill uses the latest validated reading strictly before the selected business date for each active meter; a newer draft cannot become the starting index. The bounded API query is indexed by validated station-day history.
- [x] No duplicate validation for the same meter and period (RG-005).
- [x] Closed readings locked; corrections documented and approved (RG-006). A post-close correction appends a numbered immutable adjustment to the close while preserving its original snapshot.
- [x] Lower-than-previous index blocked or controlled (REC-03); an authorized, exact-index reset record is required for meter replacement.
- [x] Rounding and precision defined per data type (RG-019): indexes and volumes use three decimals, money uses two, and tariff rates use four.

### M05 — Cash sales and collections
- [x] Cash and card collection totals are stored separately from meter-derived volume/value estimates, require an explicit per-day currency code, and do not create a sale or payment allocation.
- [x] Staff-entered card totals and manual reconciliation screen at `/app`; immutable, audited API revisions preserve recounts.
- [x] Manual reconciliation compares independent counted cash and terminal settlement against reported totals, calculates variances, and preserves recounts as numbered revisions. It is informational; agreed thresholds and close-blocking rules remain open.
- [x] Meter-volume fuel value estimate when one effective tariff covers the configured station business day; gaps and intraday tariff changes are reported as unpriced. This is not a payment allocation or issued sale.
- [x] Customer payments are separate immutable records and allocations; an allocation reduces receivables without creating a new sale (RG-013, RG-014).
- [x] Meter readings provide a separate volume/value estimate and never duplicate a posted transaction sale (RG-009, RG-010).

### M06 — Customer accounts and vouchers
- [x] Customer accounts and credit sales linked to a customer (RG-011); `/app` supports customer and credit-account setup, and the tenant ledger stores override actor/reason.
- [x] Vouchers track remaining balance; `/app` supports issue/status changes, redemption through sale tenders, and owner/manager cancellation with a required reason and an append-only balance-reconciliation movement (REC-20). PostgreSQL regression verifies source redemption history remains and the cancelled balance reaches zero.
- [x] Credit limits block sales; owner/manager override requires reason and audit (RG-012, RG-020).
- [x] Payments of earlier invoices are allocated separately and do not create new sales (RG-014).
- [x] Credit notes have immutable numbers/snapshots and can explicitly adjust customer receivables; `/app` requires an explicit receivable adjustment and reason, and each issued note has a tenant-scoped print/save-as-PDF view using the linked invoice snapshot.
- [x] Invoice snapshots are immutable and numbered, including the customer identity/contact details displayed at issuance; later customer edits do not change an issued invoice. `/app` exposes issue and print/save-as-PDF from the saved snapshot. Issuance requires accountant-approved supplied rules. Actual legal mentions/tax rules and authenticated accountant acceptance remain client decisions.
- [x] Credit sales preserve configured account terms or transaction-specific installment dates and amounts as immutable sale snapshots; later account changes do not alter existing sales.
- [x] Customer payments can target a selected saved installment; the database prevents allocations above its remaining scheduled amount. A schedule selector is shown only for scheduled sales.
- [ ] Client decision on credit-note allocation to installments, interest, late fees, and delinquency handling. Installment-targeted payment is blocked after a receivable-adjusting credit note; sale-level allocation remains available.

### M07 — Articles and stock
- [x] Article catalogue uses the shared client product catalogue; posted article sales and receipts create station-scoped immutable stock movements.
- [x] Adjustments and opening balances require a reason and audit entry.
- [x] Theoretical article stock is calculated from receipts, sales, service use, and adjustments; fuel stock additionally subtracts validated meter volumes (RG-015).

### M08 — Services
- [x] Service products have configurable, audited component recipes by station.
- [x] Posted services consume components in separate stock movements; component outflows are not counted as article sales (RG-017).

### M09 — Purchases and supplies
- [x] Tenant suppliers and immutable, posted purchase receipt records.
- [x] Fuel receptions require an active tank assigned to the matching product (RG-016).

### M10 — Daily closing and reconciliations
- [x] Daily dip entry and dated tank calibration charts; `/app` accepts supplied points as a draft and requires explicit activation. Validated dips convert by interpolation within the supplied chart range. The client must provide the tank's actual calibration points; the app does not assume tank geometry or extrapolate.
- [x] Optional cash/card variance tolerances are explicitly currency-scoped, owner/manager controlled, audited, snapshotted onto each immutable reconciliation, and reported as within/outside limits without blocking close. Threshold values and currency remain client choices; no default or escalation rule is assumed.
- [x] Operational station-day close snapshots validated meter volumes, cash/card totals and their currency, latest manual cash/card reconciliation when present, and tank dips; the close is immutable and audited.
- [x] Post-close cash/card, dip, and meter corrections preserve the original close and append immutable before/after snapshots with a reason and audit actor.
- [x] Fuel theoretical stock is compared with calibrated net dip volume and exposes the variance (RG-018); owners/managers can record a client-approved absolute tolerance per fuel product, with an audit note. No tolerance is assumed and configured flags are informational only.
- [x] Closing follows each station's configured cut-off and time-zone rule; early closes are blocked, and the business window handles daylight-saving changes.

### M11 — Reporting and exports
- [x] Daily consolidated state by station and client; `/reports/daily-state` reports only accessible stations.
- [x] Native Excel workbook, compatibility CSV, and browser print/save-as-PDF views respect tenant/client row policies; rollback checks cover report data isolation and hand-calculated sales/receivable totals by currency (RG-022, REC-17).
- [x] Neutral accounting workbook/CSV keeps sales/invoices distinct and payments separate, including installment references when supplied; target account coding, purchase-tax handling, and ERP-specific formats remain client decisions.

### M12 — Security, permissions, and audit
- [x] Audit log for sensitive operations (RG-021): append-only audit events record sensitive finance, inventory, import, onboarding, and platform actions; credit override reason is included on the sale audit event and credit ledger.
- [x] Separation of duties for credit overrides (RG-020): cashier overrides are rejected by the database, owner/manager overrides require a reason, and rollback coverage checks both paths. Two-person approval is not specified by the recorded decision and is not presumed.
- [x] Tenant-isolation tests include exports and reports (`db/tests/m5_reports.sql` verifies report and export source rows are tenant-scoped).

### M13 — Backup and continuity
- [x] Automated local rolling backup plus optional encrypted Restic repository support, with filesystem and S3-compatible backends; production credentials, endpoint, and retention policy remain unconfigured.
- [x] Local restore to a separate database demonstrated and verified through migration 048 (REC-18); the drill checks migration parity, seven RLS-protected tables (six forced), app-role privileges, M3 credit schedule and installment-allocation fields, M2 validated meter-history index, and M2 daily collection currency. Whole-second intervals are rounded up. Targets remain blank until provider/client approval; production/off-site measurements are still required.

## 10. Core domain rules to preserve

- Volume distributed, revenue, receivables, and collections are distinct measures. Credit sales are recognized before payment; later payment is not a new sale. Index-derived sales and their cash/credit split must reconcile without double-counting.
- Closed readings and validated closings are locked. Corrections require documentation and approval and retain the original trace.
- Prices are historized and frozen into each transaction. Theoretical stock does not replace physical dip readings.
- Every operational record belongs to a station and client. Server-side authorization applies to application views, reports, and exports.
